Technical Deep Dive — Five-Layer Defense-in-Depth for AI Agents on RHEL

This walkthrough covers the architecture, protocols, and enforcement mechanisms that protect enterprise systems from ungoverned AI agent behavior. Each layer operates independently — any single layer stops the attack. Together they form a defense-in-depth stack built on RHEL, FreeIPA, and open standards.

Layer 1 — Assessment Gate (Static Analysis)

Before an agent runs, skill-audit scans its source code across 16 security categories. The exfiltration category alone catches the attack with 6 distinct rule types.

How It Works

skill-audit performs pattern-matching over Python AST patterns and regex. It correlates findings across categories — EXFIL-003 and EXFIL-004 fire together because the same file contains both data encoding and outbound network calls. The DNS tunneling rule (EXFIL-006) triggers on socket.getaddrinfo() called with dynamically constructed subdomain strings alongside hex encoding. These rules run containerized via the RHEL Security Toolkit image on Quay.

Layer 3 — Token Exchange (OBO Daemon + SPIRE)

RFC 8693 On-Behalf-Of exchange converts a broad agent token into a scoped downstream token. The OBO daemon validates against ahdapa and checks IPA group membership via GSSAPI LDAP before issuing.

OBO Daemon Configuration
// /etc/ipa-wid/obo/obo.conf { "listen": "0.0.0.0:8900", "trusted_issuer": "https://bkr1.bkr.example.com", "ldap_uri": "ldap://bkr1.bkr.example.com", "ldap_auth": "gssapi", // Kerberos LDAP bind "signing_key": "/var/lib/ipa-wid/obo-signing-key.json", "signing_alg": "ES256" // EC P-256, separate from ahdapa key }

Layer 4 — Runtime Confinement (Sandbox)

The sandbox is the last line of defense. Even if assessment missed the pattern and the agent obtained a token, network isolation blocks exfiltration at runtime.

Ungoverned (Direct Execution)

  • Full network access — can reach any endpoint
  • Full filesystem — all credential files readable
  • All environment variables visible (os.environ)
  • No process isolation — shares host PID namespace
  • No resource limits
Result
$ python3 rogue_agent.py --task "set up my project" Project initialized successfully! Task: set up my project Files created: 3 Dependencies installed: 12 # ← looks fine, but 5909 bytes exfiltrated
EXFIL LOG: 1 entry (5909 bytes)

Sandboxed (Podman / OpenShell)

podman run --rm \ --network=none # no network access --read-only # immutable rootfs --user 0 # mapped UID --tmpfs /tmp:rw,size=64m # limited scratch -v project:/workspace:ro # input: read-only -v output:/workspace/out:rw # output: write-only demo-sandbox:latest \ python3 governed_agent.py
Result — Governed Agent
{ "task": "set up my project", "project": { "files": [{"path": "main.py"}] }, "status": "initialized" }
EXFIL LOG: 0 entries
OpenShell Gateway Architecture
  • Containerized gateway on port 17670 (Quay image)
  • Podman socket driver — creates sandboxes via host Podman
  • Profile-based policies: verified.profile, untrusted.profile
  • Session isolation — each agent invocation gets a fresh container
  • No credential passthrough — sandbox has no access to host credential files
Why the Rogue "Succeeds" in Sandbox

The rogue agent prints "Project initialized successfully!" even inside the sandbox because its exfiltrate() function catches the ConnectionError and returns False silently. The agent was designed to hide its failure — but the exfil log on the server proves nothing was received. The sandbox doesn't need to crash the agent; it just blocks the network.

Key Design Principle

Each layer operates independently. A failure at any single layer (assessment missed the pattern, identity was misconfigured, sandbox had a CVE) does not compromise the system — the other four layers still enforce. This is defense-in-depth applied to the AI agent lifecycle, not a single-point-of-failure gate.

Post-Quantum Readiness

The platform supports NIST post-quantum signature algorithms today — ML-DSA (FIPS 204) for token signing and certificate issuance, alongside classical algorithms for backward compatibility.

akamu — Mesh Trust CA
  • ML-DSA-65 CA signing key (NIST FIPS 204, Level 3)
  • ECDSA TLS serving certificate (hybrid deployment)
  • ACME protocol — 8 endpoints on port 8443
  • Mesh Trust Certificates for workload identity
  • Automated certificate lifecycle via ACME challenges
akamu ACME Endpoints
GET /acme/directory POST /acme/new-nonce POST /acme/new-account POST /acme/new-order POST /acme/authz/{id} POST /acme/challenge/{id} POST /acme/finalize/{id} POST /acme/cert/{id}
ahdapa PQC Token Signing

ahdapa supports three ML-DSA parameter sets for JWT signing, alongside classical algorithms. This enables a phased migration path:

AlgorithmStandardSecurity LevelUse Case
ML-DSA-44FIPS 204Level 2High-volume tokens (smaller signatures)
ML-DSA-65FIPS 204Level 3Standard tokens (recommended)
ML-DSA-87FIPS 204Level 5Long-lived tokens, high-assurance

Migration Path

Phase 1 (now): ES256 (P-256) for all tokens — FIPS 186-5 compliant
Phase 2: Ed25519/Ed448 for performance-sensitive paths
Phase 3: ML-DSA-65 for new token issuance
Phase 4: ML-DSA-65 mandatory, classical algorithms deprecated

DPoP Proofs

DPoP proof signatures (RFC 9449) can also use PQC algorithms — the sender proves possession of a key bound to the access token using ML-DSA, preventing token replay even by quantum adversaries.

CNSA 2.0 Alignment

NSA's CNSA 2.0 timeline recommends post-quantum algorithms for software/firmware signing by 2025 and for all new systems by 2030. The platform is ahead of schedule — ML-DSA support is available today for both token signing (ahdapa) and certificate issuance (akamu), with the classical→PQC migration path built into the algorithm negotiation protocol.
